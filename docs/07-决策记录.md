# 07 - 决策记录（ADR）

- 版本：v1.0（2026-09-23）
- 说明：每条 ADR 记录一个**不易推翻或影响广泛**的决策。新增追加在文末，**不修改已"已决定"条目的结论**（要推翻就新增一条"取代 ADR-00X"）。
- 状态枚举：`已决定` / `待定` / `已废弃`

格式：
```
## ADR-00X 标题
- 状态 / 日期
- 背景
- 决定
- 理由
- 影响（代价与约束）
```

---

## ADR-001 使用原生 Android（Kotlin），不使用跨端框架

- 状态：已决定 / 2026-09-23
- 背景：本项目核心是 BLE 长连接、前台服务、系统级通知、后台保活。跨端框架（Flutter/React Native/Expo）在这些系统能力上需要大量原生桥接，坑多且调试链路长。
- 决定：原生 Android + Kotlin + Jetpack Compose。
- 理由：① BLE/前台服务/通知的原生 API 完整可控；② Compose 已成熟且体验现代；③ 单平台（只做 Android）没有跨端收益；④ AI 辅助开发原生 Kotlin 的资料与准确性最好。
- 影响：只做 Android；不引入跨端技术栈；未来若要 iOS 需重写（协议层纯 Kotlin 逻辑可移植参考）。

## ADR-002 单 Gradle 模块 + 严格包分层，协议层零 Android 依赖

- 状态：已决定 / 2026-09-23
- 背景：多模块工程编译与维护成本高，单人 + AI 协作规模下收益有限；但协议解析必须可脱离硬件/模拟器单测。
- 决定：单一 `app` 模块，按 `core/*`、`feature/*` 包边界分层；`core/protocol`（以及 domain 纯逻辑）禁止 import 任何 Android 类。
- 理由：兼顾简单与可测；违反边界的问题在 code review 中检查（必要时后续引入 ARCH 单元测试约束）。
- 影响：编译快、结构简单；当模块膨胀到影响编译速度或需要复用时，再拆 library module（届时新增 ADR）。

## ADR-003 通知走纯本地，不建服务器、不接 FCM

- 状态：已决定 / 2026-09-23
- 背景：设备通过 BLE 直连手机，手机和雷达物理上在一起（寝室）。通知需求全部由本地事件触发。
- 决定：全部通知由 App 本地产生；不引入任何后端、账号、云推送。
- 理由：架构极简、零运维、隐私最好；FCM 在这里没有数据源可接。
- 影响：手机离开蓝牙范围就收不到事件（产品上可接受，场景决定）；若未来要远程接收，需要网关设备（ESP32 中继）——届时新增 ADR。

## ADR-004 后台保活以前台服务为主，辅以系统引导与 WorkManager 兜底

- 状态：已决定 / 2026-09-23
- 背景：24h BLE 监控与国产 ROM 省电策略冲突（docs/05 难点 2）。
- 决定：监控开启 = 前台服务（connectedDevice）+ 常驻通知；引导用户加白名单；WorkManager 周期兜底检查；开机自动恢复。
- 理由：前台服务是唯一合规且可靠的长驻手段；不使用任何灰色保活技巧（双进程/无声音乐等）。
- 影响：状态栏有常驻通知（设计上把它做成"有用的状态卡片"而非负担）；极端 ROM 下仍可能被杀 → 至少保证断连告警与自动恢复。

## ADR-005 事件与配置存 Room，设置项存 DataStore

- 状态：已决定 / 2026-09-23
- 背景：需要事件时间线、配置模板、设备档案；查询需求简单。
- 决定：Room（DeviceProfile / RadarEvent / ConfigSnapshot / ConnectionSession）+ Preferences DataStore（通知策略等设置）。不引入网络层缓存框架。
- 理由：官方标准、与 Flow 集成好、可单测。
- 影响：事件表需保留策略（默认 30 天或 5 万条）防无限增长。

## ADR-006 先做"变化检测 + 节流"的通知引擎，不做智能场景识别

- 状态：已决定 / 2026-09-23
- 背景：曾考虑"有人停留超过 X 分钟才提醒"等复杂规则。
- 决定：第一版只实现：状态边沿触发、最小间隔节流、免打扰时段、三档监控模式。复杂规则（停留时长、时段组合）待真实使用反馈后再加。
- 理由：避免过度设计；通知引擎的规则表结构已为扩展留好口子。
- 影响：无。

## ADR-007 OTA 固件升级暂缓，阶段 5 再评估

- 状态：已废弃（被 ADR-009 取代）/ 2026-09-23
- 背景：官方 App 支持 OTA 升级雷达固件，但固件包的分发渠道未知（可能内置于官方 App 或其服务器）。
- 决定：阶段 0 实测官方 App 时调研 OTA 流程与固件来源；若无法合法获得固件包，则放弃该功能，App 内提示"请用官方 App 升级固件"。
- 理由：不逆向、不抓取官方私有接口（原则见 PRD 范围外条目）。
- 影响：P0 复刻清单中 OTA 标注为"可豁免项"。

## ADR-008 USB-OTG 串口直连不纳入近期范围

- 状态：待定 / 2026-09-23
- 背景：设备同时有 UART；手机 + OTG + USB 转串口可以绕过 BLE（更稳定、无单连接限制）。
- 决定：近期只做 BLE；架构上 `RadarConnection` 不假设传输层一定是 BLE（输入输出都是字节流），未来可加 SerialTransport 实现。
- 理由：用户的部署方式是纯供电 USB，串口直连手机不符合实际使用场景；属于调试便利功能。
- 影响：无。

## ADR-009 OTA 固件升级为必做功能，采用"本地固件文件"方案（取代 ADR-007）

- 状态：已决定 / 2026-09-23（取代 ADR-007 的"暂缓"）
- 背景：项目所有者要求全量复刻官方 App 能力（PRD 4.1 第 10 项），OTA 不可豁免。ADR-007 原方案卡在"官方固件分发渠道未知"，但换思路即可解耦：固件包不需要从官方服务器下载，用户可自行从官方资料页/客服获取 `.bin`，App 负责"选文件 → 传输 → 校验 → 重启"的完整执行链路。
- 决定：App 实现 OTA 全流程，固件来源 = 本地文件选择器（SAF）+ 0x00C0 使能 + 分包传输（传输协议细节研读官方 Demo OTA 模块后回填 docs/03）。App 同时做基本的安全防护：提示电量/距离/勿断电，传输中断可安全重试。
- 理由：把"要不要做"与"固件从哪来"解耦；不逆向、不接官方私有接口的原则不变；这样既全量复刻又不留功能豁免。
- 影响：阶段 5 交付物从"评估"改为"实现"；`core/protocol` 需增加 OTA 传输帧编解码与断点重传逻辑；ADR-007 标记为被取代。
