## 1. 技术选型

| 领域 | 选型 | 一句话理由 |
|---|---|---|
| 平台/语言 | 原生 Android / Kotlin 2.x | BLE 长连接 + 前台服务 + 通知是本项目的命脉，原生最可控（对比见 ADR-001） |
| UI | Jetpack Compose + Material 3（动态取色、深色模式） | 现代化体验要求；声明式 UI 与 Flow 天然契合 |
| 架构模式 | MVVM + UDF（单向数据流） | 状态来源清晰，调试工具类页面尤其受益 |
| DI | Hilt | 标准方案，测试时可替换 Fake |
| 异步 | Kotlin Coroutines + Flow（StateFlow/SharedFlow） | BLE 回调 → Flow 是标准做法 |
| 本地存储 | Room（事件/设备/配置快照）+ DataStore（设置项） | 结构化与轻量配置分开 |
| 后台 | Foreground Service（`connectedDevice`）+ WorkManager 兜底 | 见 ADR-005 |
| 通知 | 本地 NotificationManager，无服务器 | 见 ADR-004 |
| 构建 | Gradle KTS，minSdk 26 / targetSdk 最新 | |

## 2. 总体架构

```
┌─────────────────────────── UI 层（feature/*，Compose）──────────────────────────┐
│  扫描连接   设备主页   参数配置   工程模式   事件时间线   日志   设置   部署向导   │
└───────────────────────────────────▲──────────────────────────────────────────┘
                                     │ StateFlow（UiState）/ 事件
┌─────────────────────────── 领域层（domain/*）───────────────────────────────────┐
│  UseCase：ConnectDevice / ObserveRadarState / UpdateSensitivity /               │
│           RecordEvent / EvaluateNotification ...                                │
│  纯 Kotlin Model：RadarState、DeviceConfig、RadarEvent ...                      │
└───────────────▲───────────────────────────────▲────────────────────────────────┘
                │                               │
┌───────────────┴────── 数据层 ──┐  ┌───────────┴──────── 设备通信层 ────────────┐
│ DeviceRepository               │  │ BleClient（GATT 封装、操作队列、重连状态机）│
│ EventRepository（Room）        │  │ Ld2410Protocol（帧编解码，零 Android 依赖）│
│ ConfigRepository（Room+快照）  │  │ RadarConnection（协议之上的设备会话抽象）  │
│ SettingsRepository（DataStore）│  │                                            │
└────────────────────────────────┘  └────────────────────────────────────────────┘
                ▲                               ▲
┌───────────────┴────────────── 后台层 ─────────┴───────────────────────────────┐
│  RadarMonitorService（前台服务）：持有连接，驱动监控                              │
│  NotificationEngine：事件 → 规则评估 → 节流/合并 → 渠道分发                     │
│  BootReceiver / WorkManager：开机与定期兜底恢复                                 │
└───────────────────────────────────────────────────────────────────────────────┘
```

**核心原则**：`core/protocol` 与 `domain` 是零 Android 依赖的纯 Kotlin，可 100% 本地单测（无硬件、无模拟器）；Android 相关全部隔离在 ble/data/service/ui。

## 3. 核心组件设计

### 3.1 BleClient（core/ble）

对 Android GATT 的薄封装，职责单一：

- **操作串行队列**：GATT 操作必须串行（上一条回调回来才能发下一条），内部用协程 Mutex + Channel 实现 `suspend fun enqueue(op)`；
- **状态机**：`Disconnected → Scanning → Connecting → DiscoveringServices → Authenticating → Ready`；任何一步失败进入 `Failed(reason)` 并触发重连策略；
- **自动重连**：指数退避（1s→2s→5s→15s→60s 封顶），用户手动断开则不重连；
- **MTU**：连接后请求 MTU=247（失败就用默认 23，不影响功能，只影响分包数）；
- 输出：`Flow<BleEvent>`（Connected/Data(bytes)/Disconnected/Error），不认识协议内容。

### 3.2 Ld2410Protocol（core/protocol，纯 Kotlin）

- `FrameDecoder`：**增量流式解码器**，`fun feed(bytes): List<Frame>`，内部缓冲 + 帧头扫描 + 长度/帧尾双校验（细节见 docs/03 §5）；
- `Frame` 密封类：`ReportFrame.Basic(...)` / `ReportFrame.Engineering(...)` / `AckFrame(command, status, payload)` / `Unknown`；
- `CommandBuilder`：类型安全的命令构造（`enableConfig()`、`setMaxGates(...)`、`setGateSensitivity(...)`、`authenticate(password)` ...），产出字节数组；
- 全部用官方 PDF 中的示例字节流做黄金测试样本（Golden Test）。

### 3.3 RadarConnection（core/device 或 domain 层）

协议之上的"设备会话"抽象，对上暴露有意义的 API：

- `suspend fun connect(mac)`：编排 BLE 连接 → 服务发现 → 开 Notify → 0x00A8 鉴权 → 读固件/MAC/参数（能力探测）；
- `val radarState: StateFlow<RadarState>`：最新上报解析结果（有人状态、距离、能量、各门数据）；
- `suspend fun <T> config(block)`：配置会话模板方法（自动 0x00FF/0x00FE 包裹、串行发命令、超时重试）；
- 断线 → 事件 → 通知引擎 + 自动重连。

### 3.4 RadarMonitorService（service/）

- 前台服务，`foregroundServiceType="connectedDevice"`，常驻通知显示当前状态（已连接·有人/无人·最后事件）；
- 持有 `RadarConnection`，把雷达状态流转成两类输出：**事件入库** + **通知评估**；
- 生命周期策略：用户开启"后台监控"才启动；手动停止/设备用户主动断连即退出。

### 3.5 NotificationEngine（core/notification）

- 输入：`RadarEvent`（状态变化、连接事件、异常、调试信息）；
- **规则评估**：按用户设置（开关、渠道、最小间隔、免打扰时段、是否只在有人时提醒）过滤；
- **节流器**：同类事件在窗口期内合并为一条汇总（"过去 5 分钟有 3 次活动"）；
- 输出：四个通知渠道 —— `检测` / `设备状态` / `调试` / `常驻`；
- 纯逻辑（除最终 `notify()`），可单测。

### 3.6 数据模型（Room）

| Entity | 关键字段 | 说明 |
|---|---|---|
| `DeviceProfile` | mac(主键)、alias、备注、lastSeen、lastFirmware、能力位(分辨率/底噪/光敏) | 设备档案 |
| `RadarEvent` | id、deviceMac、timestamp、type、severity、payload(json) | 事件流水（有人/离开/断连/重连/配置变更/异常） |
| `ConfigSnapshot` | id、deviceMac、timestamp、name、configJson | 配置模板与历史快照（"应用模板"=写参，"差异对比"=读参对比） |
| `ConnectionSession` | id、deviceMac、start、end、disconnectReason、rxFrames、lossCount | 连接质量统计 |

事件保留策略：默认保留最近 30 天或 5 万条，先到先删（设置可调）。

### 3.7 日志系统

- 运行日志：分级（D/I/W/E），内存环形缓冲（约 2000 条）+ 可选落盘；
- 原始帧日志：调试模式开启后记录收发十六进制流，用于协议问题排查；
- 导出：打包为 zip（日志 + 事件 CSV + 当前配置），系统分享出去。

## 4. 关键流程

### 4.1 连接建立时序

```
UI: 点击设备
 └> RadarConnection.connect(mac)
     ├> BleClient.connect → 服务发现 → 启用 fff1 Notify → 请求 MTU
     ├> 发送 0x00A8(密码) ── 等 ACK ── 失败则提示改密码/重试
     ├> 0x00FF 使能配置 → 0x00A0 读固件 → 0x00A5 读 MAC → 0x0061 读参数
     │   → （能力探测）0x00AA 查距离分辨率 → 0x00FE 结束配置
     └> 进入 Ready：上报帧 → FrameDecoder → RadarState → UI/事件/通知
```

### 4.2 事件→通知时序

```
上报帧(状态 无人→有人)
 └> RadarConnection: 状态去抖/变化检测 → RadarEvent.HumanAppeared
     ├> EventRepository.insert
     └> NotificationEngine.evaluate
         ├─ 规则：检测通知开？免打扰中？节流窗口内？
         └─ 通过 → NotificationManager.notify(渠道=检测, 点击→事件详情)
```

## 6. 权限清单（AndroidManifest 预告）

| 权限 | 用途 | 备注 |
|---|---|---|
| `BLUETOOTH_SCAN` / `BLUETOOTH_CONNECT` | BLE 扫描/连接 | API 31+；声明 `neverForLocation`（扫描过滤按名称/服务 UUID，不需要定位） |
| `ACCESS_FINE_LOCATION` | 兼容 API 26–30 的 BLE 扫描 | 仅旧系统需要，运行时申请 |
| `POST_NOTIFICATIONS` | 通知 | API 33+ 运行时申请 |
| `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_CONNECTED_DEVICE` | 前台监控服务 | API 34 要求声明类型 |
| `RECEIVE_BOOT_COMPLETED` | 开机恢复监控 | 可选能力 |

## 7. 扩展性设计（为未来留的口子）

- **新命令**：只需在 `CommandBuilder` + 命令表加一条，不动架构（V1.09 新命令即按此接入）；
- **新型号雷达**（如 LD2410B/S、LD2450）：`Ld2410Protocol` 抽象出 `RadarProtocol` 接口的时机放在"真的接入第二个型号"时，现在不做过度抽象；
- **多设备**：数据模型已按 deviceMac 维度设计；`RadarConnection` 可实例化多个；UI 多设备支持留到 P2；
- **通知渠道扩展**：新事件类型 → 新规则即可，Engine 不需要改结构；
- **跨对话维护**：任何架构变化必须同步本文档 + 新增 ADR（见 README 协作规则）。
