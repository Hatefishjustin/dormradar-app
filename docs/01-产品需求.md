# 01 - 产品需求文档（PRD）

- 版本：v1.1（2026-09-23）
- 状态：已确认
- 作者：项目所有者 + AI（产品/架构角色）
- v1.1：吸收《官方 APP 功能全量复刻清单》（docs/reference/），确立"两层信息架构"，OTA 升级为必做（见 ADR-009）

## 1. 背景与问题

寝室门上安装了一块 HLK-LD2410C 毫米波雷达（USB 供电，门板内侧朝向走廊），用于感知门外是否有人经过、停留或活动；设备 OUT 引脚接 LED，检测到人体时亮灯。

官方已有 App（HLKRadarTool），但存在以下痛点：

- 官方 App 是"调参工具"定位，**不具备后台监控能力**：必须打开 App、保持前台、手动连接，才能看到设备状态；
- 设备一旦装进门板，就成为"黑盒"：它什么时候触发了、有没有掉线、配置是否还正常，完全无法得知；
- 没有事件历史，无法回溯"昨晚 3 点是不是有人经过"；
- 调参体验陈旧，对"穿门探测"这种需要反复试错的场景支持不足。

## 2. 产品定位

一个 App，四个角色：

| 角色 | 解决的问题 |
|---|---|
| **控制工具** | 完成官方 App 能做的所有配置与控制（复刻目标） |
| **监控工具** | 后台常连设备，实时掌握"有人/无人、距离、能量"，异常立即通知 |
| **调试工具** | 工程模式能量图、原始帧日志、连接质量统计、日志导出 |
| **部署辅助工具** | 底噪检测、安装角度/灵敏度调优、配置模板、部署后健康观察 |

一句话：**从第一次连接，到安装调试，再到长期无人值守运行，全部用这个 App 完成。**

## 3. 典型场景故事

1. **首次调试**：雷达拿在手里 → App 扫描发现 → 一键连接（自动完成蓝牙密码验证）→ 实时显示有人/无人、目标距离、能量值 → 调整灵敏度并实时看到效果。
2. **安装部署**：设备固定到门板内侧 → 打开"工程模式"看各距离门能量分布 → 用"底噪检测"自动测量走廊环境噪声 → 根据建议设置各门灵敏度，屏蔽门内房间侧（避免自己在屋里走动触发）→ 保存为配置模板"门板部署 v1"。
3. **日常运行**：App 退到后台，前台服务保持 BLE 连接 → 走廊有人经过时手机收到通知（可配置为仅震动/静默记录）→ 事件自动记入时间线。
4. **异常排查**：手机收到"设备断开"通知 → 打开 App 看连接日志与断开时间点 → 发现是 USB 供电松动，重新插拔后自动重连恢复。

## 4. 功能需求（按优先级分层）

### 4.0 信息架构：两层设计（体验总原则）

用户明确要求：**功能全量复刻，但"刚需的浅、专业的深"**。全 App 固定两层信息架构：

| 层 | 定位 | 内容 | 设计原则 |
|---|---|---|---|
| **简单层**（首页 + 引导流程） | 覆盖 90% 日常使用 | 连接/断开、实时状态大卡片（有人/无人 + 距离/能量）、一键设置（推荐参数包）、灵敏度自动配置（底噪检测引导式流程）、通知开关、工程模式入口 | 常用动作 ≤2 次点击；默认值合理到"不进详细设置也能用得很好" |
| **详细层**（"详细设置"页组） | 调参/排障/专业用户 | 距离门灵敏度矩阵、最远探测距离、无人持续时间、距离分辨率、光敏联动、串口波特率、蓝牙开关/改密、门限值、恢复出厂、重启、OTA | 面向"知道自己在改什么"的用户；每项带专业说明文案 + 一键恢复默认 |

导航骨架：底部导航 3 Tab —— **首页（监控）** / **事件** / **设置**；"详细设置"从设置页二级进入，设备级专业项集中在设备详情内。

### 4.2 P1 — 体验增强（超越官方）

| 模块 | 功能 |
|---|---|
| **后台监控** | 前台服务保持 BLE 常连，App 不在前台也持续接收数据 |
| **消息通知** | 见第 5 节（本项目的核心增量能力） |
| **事件时间线** | 有人出现/离开、连接断开/恢复、配置变更、异常，全部带时间戳入库可查 |
| **设备档案** | 设备别名、备注（"寝室门板内侧"）、最后在线时间、当前配置快照 |
| **自动重连** | 断线后指数退避自动重连，恢复时通知 |
| **连接质量** | RSSI 曲线、丢帧率、重连次数统计 |
| **日志系统** | 分级运行日志 + 可选原始帧十六进制记录，支持导出分享 |
| **配置模板** | 把整套参数（距离门/灵敏度/无人时长）存为模板，一键应用/对比差异 |
| **现代化 UI** | Material 3 + 动态取色 + 深色模式；普通模式极简，调试模式信息密度高 |

### P2 — 长期方向（不在近期范围，但架构要留好口子）

- 统计与洞察：走廊人流热力（按小时/星期聚合事件）
- 桌面小组件 / 快捷磁贴（实时有人状态）
- 多设备管理（架构上支持，UI 后期再做）
- USB-OTG 串口直连（有 USB 转串口硬件时绕过 BLE，见 ADR-008）
- 数据导出 CSV / 与智能家居（Home Assistant）联动

> 注：OTA 已从 P2 提升到 P0（见 4.1 第 10 项与 ADR-009）。

## 5. 通知体系需求（核心增量能力）

### 5.1 触发事件分类

| 类别 | 事件 | 默认重要性 |
|---|---|---|
| 检测事件 | 无人→有人（出现）、有人→无人（离开）、持续有人超过阈值 | 中（可配） |
| 连接事件 | 连接断开（非用户主动）、重连成功、重连多次失败 | 断开/失败：高；恢复：低 |
| 设备事件 | 设备重启痕迹（连接恢复但运行状态异常）、配置被外部修改（读取值与快照不一致） | 中 |
| 调试事件 | 调试模式开启时：每次状态变化、每次命令 ACK、异常帧 | 低 |

### 5.2 通知策略（防打扰是硬需求）

- **状态变化才通知**：默认只在 无人↔有人 切换时通知，不每秒轰炸；
- **节流**：同类通知可配置最小间隔（如 1 分钟），间隔内事件合并为"期间又有 N 次活动"；
- **免打扰时段**：可设置时间段内静默（仅记录，不提醒）；
- **分级渠道**：
  - `检测` 渠道：有人出现等，可单独设铃声/震动/静默；
  - `设备状态` 渠道：断开/恢复/异常；
  - `调试` 渠道：默认关闭，排查问题时开启；
  - `常驻` 渠道：前台服务的低优先级常驻通知（显示当前状态：已连接·有人/无人·最后事件时间）。
- **点击通知**直达对应页面（事件详情 / 设备状态页）。

### 5.3 通知用于调试

通知不只是提醒，更是远程观察手段：通知历史即设备运行日志的摘要。事件时间线中每条记录可从通知跳转定位。

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 稳定性 | 后台监控 24h+ 不崩溃；断线必须可自动恢复 |
| 低耗电 | 前台服务常驻但不得频繁唤醒；无动画时 UI 不刷新 |
| 响应性 | 连接后 1 秒内出实时数据；配置命令有明确成功/失败反馈 |
| 兼容性 | minSdk 26（Android 8.0）起；适配国产 ROM 的后台限制并给出引导 |
| 隐私 | 全部数据本地存储，无账号、无云同步、无第三方统计 |
| 可维护性 | 协议层零 Android 依赖可单测；文档与代码同步演进 |
| 可交接性 | 见 README 的协作规则（本项目硬指标） |

## 7. 明确不做（当前阶段）

- 不做服务器/云端/账号体系（通知走本地，不走 FCM）——见 ADR-004
- 不做 iOS
- 不做设备固件修改（只使用官方协议能力）
- 不破解/修改官方 App（仅参考其公开协议与官方 Demo）

## 8. 成功标准

1. 官方 App 能对设备做的操作，本 App 都能做（对照 4.1 十六项验收全绿）；
2. 设备装进门板后，**手机放口袋里也能知道走廊有人经过**（通知到达率接近 100%，以一周实测为准）；
3. 出现"误报/漏报"时，仅凭 App 内的工程模式+日志就能定位原因，不需要把设备拆下来接电脑；
4. 任何一个新 AI 对话，只读本仓库文档即可继续开发（交接机制有效运转）。
