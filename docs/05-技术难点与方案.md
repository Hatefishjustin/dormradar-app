# 05 - 技术难点与应对方案

- 版本：v1.0（2026-09-23）
- 状态：已确认

每个难点按「问题 → 方案 → 验证方式」组织。

---

## 难点 1：BLE 数据的分包与粘包（必然遇到）

- **问题**：默认 MTU 23 → 每个通知最多 20 字节；工程模式上报帧约 45 字节，必然被切成多片到达，也可能多帧粘在一个通知里。直接按"一次回调=一帧"解析必挂。
- **方案**：`FrameDecoder` 做成**增量流式解码器**（docs/04 §3.2）：内部维护字节缓冲，循环扫帧头 → 校验长度与帧尾 → 出帧；数据不足则等下一次 `feed`。同时记录"废字节"统计，用于连接质量监控。
- **验证**：黄金测试——把官方 PDF 示例帧人工切片（1B/7B/20B 随机切）后喂入，断言输出一致。

## 难点 2：后台长期保活（国产手机是最大的坑）

- **问题**：小米/华为/OPPO 等 ROM 激进杀后台，BLE 长连接 + 24h 监控与系统省电策略天然冲突。
- **方案（多层叠加）**：
  1. 监控开启时用**前台服务**（`connectedDevice` 类型）+ 常驻通知——这是合规且最有效的手段；
  2. 引导页检测厂商并提示用户：允许自启动、关闭电池优化、锁定后台（用 `canDeviceLocked` 类引导话术，跳对应系统设置页）；
  3. `WorkManager` 周期性兜底任务：检查"应连未连"则尝试重连/重启服务；
  4. 开机广播 `BOOT_COMPLETED` 恢复监控（用户开启过的话）；
  5. 断连后本地指数退避重连（见 docs/04 §3.1）。
- **验证**：阶段 3 验收 = 主力机实测 24h+ 不断连（或有断连必自动恢复且有事件记录）。

## 难点 3：通知风暴（自己把自己烦死）

- **问题**：走廊高峰期每秒都可能有状态波动，无脑通知会让用户立刻关掉通知权限。
- **方案**：通知引擎三级防线（docs/04 §3.5）：
  1. **变化才报**（默认只报 无人↔有人 边沿）；
  2. **节流合并**（最小间隔可配，窗口内合并为汇总条）；
  3. **免打扰时段**（静默记录不提醒）。
  另有总开关"监控模式"：`静默记录`（只入事件库）/ `有人提醒` / `全量调试`。
- **验证**：模拟 10 分钟内 50 次状态变化，断言通知条数 ≤ 配置上限；真实部署一周感受。

## 难点 4：固件版本差异与能力探测

- **问题**：市面 LD2410C 固件版本不一（V1.09 协议里的距离分辨率 0.2m、底噪检测、辅助控制、工程帧尾部光照/OUT 字段都依赖固件）。按固定版本写死解析必然出错。
- **方案**：
  - 连接后做**能力探测**（docs/04 §4.1）：读固件版本 + 试探性查询（失败即标记不支持），结果存入 `DeviceProfile.能力位`；
  - 解析器对可选字段按帧长度容错（有则解析，无则跳过）；
  - UI 按能力位显示/隐藏对应功能入口，并提示"该功能需更高固件版本"。
- **验证**：用不同长度的合成帧做解析单测；阶段 0 实机确认本设备的固件版本与能力。

## 难点 5：BLE 单连接冲突

- **问题**：设备只允许一个主机连接。官方 App 连着时，本 App 连不上（反之亦然），用户会困惑。
- **方案**：
  - 连接失败时识别"被占用"特征（GATT 连接被拒/立即断开），给出明确提示："设备正被其他 App（如官方 HLKRadarTool）占用，请断开后再试"；
  - 检测到官方 App 包名时可额外提示（可选，非必需）；
  - 后台监控期间被抢占 → 记事件 + 通知 + 自动重连夺回。
- **验证**：官方 App 与本 App 互抢连接的实测剧本（写入阶段 0 实测清单）。

## 难点 6：无硬件时的开发效率

- **问题**：不可能每改一行代码都拿真机试；协议解析、通知规则、事件入库都应脱离硬件开发。
- **方案**：
  - `core/protocol`、`NotificationEngine`、Repository 全部纯 Kotlin 可单测；
  - `FakeRadarSource`：实现与 `RadarConnection` 相同接口，按脚本回放状态序列（可模拟"有人 3 秒 → 无人 → 断连 → 重连"），UI 层可无硬件联调；
  - 真机录制的原始帧流存为测试资源，回放验证解析器。
- **验证**：CI 跑全部单测；开发者选项里提供"使用模拟数据源"。

## 难点 7：穿门场景的误报/漏报调优（产品级难点）

- **问题**：隔着门板能量衰减大，灵敏度太高误报（风吹草动）、太低漏报（人走过没反应）。这是用户真实使用中最耗时的部分。
- **方案**（产品化而非只给参数页）：
  1. **底噪检测引导**：一键开始 → 显示各门环境底噪 → 按"底噪 + 安全余量"自动建议灵敏度；
  2. **部署向导**：引导用户完成"走廊有人走一遍 / 走廊无人静置 5 分钟"两个采样动作，对比给出建议参数；
  3. **事件回看调参**：误报时段的事件可跳转查看当时的能量分布截图（工程模式快照），据此抬高对应门灵敏度；
  4. 配置模板对比：改参前后各存快照，一键回滚。
- **验证**：阶段 4 实测——用向导完成一次部署调参，记录误报率是否下降。

## 附：安全与隐私

- 全部数据仅存本机（Room/文件），不联网、不上报；
- 蓝牙密码以 Android Keystore 加密存储（用户改过默认密码时）；
- 导出的日志 zip 不含密码字段。
