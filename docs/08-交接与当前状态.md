## 2. 已确认的关键事实（不用重新调研）

1. 设备 = HLK-LD2410C，BLE 从机、单连接；**BLE 上跑的就是串口协议**；
2. BLE 特征：`fff1` = Notify（设备→手机），`fff2` = Write Without Response（手机→设备）；服务 UUID `0000fff0-0000-1000-8000-00805f9b34fb`（官方 Demo 源码确认）；MTU 主动请求 247，写类型固定 WRITE_TYPE_NO_RESPONSE；
3. 连接后必须先发**蓝牙密码**（命令 0x00A8，默认密码 `HiLink`）验证，通过后设备才透传数据；
4. 命令帧头 `FD FC FB FA` / 尾 `04 03 02 01`；上报帧头 `F4 F3 F2 F1` / 尾 `F8 F7 F6 F5`；全部小端；
5. 配置类命令必须用「使能配置 0x00FF → …… → 结束配置 0x00FE」包裹；
6. 协议版本 V1.09（2025-06-09）新增（命令字已从官方 Demo `BaseVolume.kt` 核对回填 docs/03）：距离分辨率设置 `0x00AA`/查询 `0x00AB`、光敏/辅助控制设置 `0x00AD`/查询 `0x00AE`、底噪检测 `0x000B`（固定 60s）、门限值设置 `0x00C4`/查询 `0x00C5`；
7. 官方提供**安卓蓝牙 Demo 源码**和 PC 上位机，是连接细节的权威参考；
8. 蓝牙被关闭后的恢复：2~3 秒内断电重上电 5 次；
9. 串口默认波特率 256000（仅备用调试通道用得到）；
10. 技术栈已定：原生 Android + Kotlin + Compose + Hilt + Room + 前台服务 + 本地通知（理由见 docs/07）；
11. **真机实测（2026-09-27，Redmi Note 11 / API 33）**：广播名 = `HLK-LD2410_<MAC末4位>`（本机 HLK-LD2410_635B）；固件 1.00.68（构建 0217090725），0x00AB 有响应（支持 0.2m 分辨率切换）；本机当前参数：运动门 8/静止门 6、无人 2s、分辨率 0.75m；鉴权/探测/上报时序与 docs/02 §2 一致；
12. **MIUI 会丢弃 Log.d/Log.v**（默认日志级别），关键事件必须用 Log.i 及以上（已改）；
13. **雷达不广播的排查经验**：本例为模块内部短路所致（用户拆机修复）；另有两类常见原因——被其他设备独占连接（单连接特性）、蓝牙被 0x00A4 关闭（用 2~3 秒断电重上电 ×5 的仪式恢复）；
14. **光敏 state 编码已确认（2026-09-27，官方 Demo `DeviceState.getPhotosensitiveStateHttp`）**：`0x00`=关闭 / `0x01`=光感低于阈值触发 / `0x02`=光感高于阈值触发；阈值 0~255（默认 0x80）；OUT 电频（`0x01`=高电平）是 0x00AE 响应的第 3 字节（固件 ≥2.01.23021610），**不是 state 的位**。本机固件 1.00.68 属旧固件，光敏能力待真机用 0x00AE 探测（不支持则 UI 自动降级）；
15. **门限值 0x00C5 返回布局存疑（官方 Demo 按无标准状态字口径解析，`0x01`=成功）**：本 App 做了双布局容错（`AckParsers.parseThreshold`），真机验收时确认实际布局并收敛（预计本机旧固件不支持该命令）；
16. **底噪检测的进度与结果**：官方 Demo 不用 0x001B，而是靠上报帧目标状态 `0x04`=进行中 / `0x05`=成功 / `0x06`=失败；检测即"灵敏度自动配置"，成功后设备自动写入建议灵敏度（本 App 成功后回读 0x0061 展示）。
17. **0x0061 响应布局真机确认（2026-09-27，曾栽过跟头）**：`0xAA + 最大距离门N + 配置运动门 + 配置静止门 + (N+1)×2 灵敏度 + 无人时长(2B)`——首字节后是**最大门**（硬件门数上限，本机恒 8），不是运动门。ESPHome `ld2410.cpp`（buffer_data_[12]/[13]）与官方 Demo 双重印证。
18. **0x000B 底噪检测自带时长参数（2B 秒）**：官方 Demo 固定发 60s；本 App 已开放 30/60/120 三档，非 60 档是否被旧固件尊重待观察（Q9）。
19. **近门（门 0/1）静止灵敏度部分固件不可写**：0x0064 写入会被拒绝（ACK 失败）；本 App 在 `applySensitivityTable` 做了 fallback（该门只写运动通道，回读校验放行被拒门），日志会记 Log.i。
20. **首页「检测距离」= 协议 detect 字段直读，未经任何平滑（2026-09-28 审计确认，重要）**：`HomeViewModel.smoothDisplay()` 的 `new.copy(...)` **只覆盖 move/static 两个通道的距离与能量**，`detectDistanceCm` 原样保留；而首页状态卡、数据网格的「检测距离」行、`RadarScopeCard` 目标点全部读 `displayState.detectDistanceCm`。
    - 推论：**「距离跳动由显示层放大」这一假设在构造上不成立**——UI 的 detect 距离 ≡ 原始帧值，唯一偏离是 `TARGET_HOLD_MS=2000` 的「丢失保持」窗口（无人帧到达后 2 秒内继续显示旧距离）。诊断取证时若把保持窗口的行当成"显示层在编造数据"，会得出完全错误的结论。
    - 因此距离抖动只可能来自：设备 detect 字段自身噪声／环境多径／固定物回波／目标真实移动。
21. **设备在无人时上报 detect = 0**（不是固定值噪声）：判定「固定物回波」必须用"**无人时仍报非零且恒定**"作为特征，不能只看"读数是否恒定"，否则会把正常的 0 误判成回波（`DistanceDiagAnalysis` 已按此实现并固化单测）。
22. **「底噪检测」与「无人基线定参」不冲突，但不能同时进行（2026-09-28 确认）**：
    - 命令层面互不干扰：设备侧是 `0x000B`，App 侧是 `0x0064`，且都经 `RadarConnection.configMutex` 串行；
    - **真正的陷阱是时序**：`0x000B` 是个设备侧后台进程，`0x00FE` 结束配置后它仍在跑；**结束时会自动写入设备自己的建议灵敏度表**，会把 App 刚写入的 `0x0064` 阈值覆盖掉。而且检测期间（上报帧目标状态 `0x04`）的帧不是正常目标数据，拿它当样本没有意义；
    - 防护：`EnergySeriesCollector` 在采样期间监听目标状态，一旦见到 `0x04` 就置位 `noiseDetectionRunning`，ViewModel 据此**作废本次样本**并提示等待；
    - 定位是互补：设备侧检测给基准（实测偏高、不够灵敏），无人基线定参把阈值压到"刚好高于环境浮动"（更灵敏）。用户抱怨"底噪检测完还是偏高"时，正确处置就是用无人基线定参再压一次。
23. **有无导阶段标记决定了能否算出误报率（2026-09-28）**：按"设备自报有人/无人"分段是循环论证——拿设备的判断去评估设备的判断，只能得到读数分布，算不出误报率。只有按 App 指挥的阶段标记分段，"无人阶段里设备判有人的帧占比"才是真正的误报率。旧格式 CSV（`phase=0`）会被 `DistanceDiagAnalysis` 自动识别并退回旧口径，同时在 findings 里提示重采。
24. **「近场饱和」——一种阈值完全无解的失效模式（用户 2026-09-28 实测确认，重要）**：
    - **现象**：隔着门板（复合门）时距离读数被**钉在最小值附近**（用户实测恒定 30cm），**无人时也判"有人"**；但灵敏度页的实时能量柱在人的真实位置**仍有一点点起伏**——信号存在，只是被压住了。
    - **机理**：紧贴天线的介质（门板/玻璃/金属）既是衰减体、也是强反射体。当它的回波强度**超过**门外人体回波时，雷达总是优先报最强回波 → 距离被钉在最近的距离门；人体只剩能量柱上的一点起伏。
    - **关键结论：这种局面任何阈值都无效**。阈值只是"门槛"，只能筛掉比它弱的信号；当干扰本身强于目标时，抬高门槛会把人一起屏蔽，压低则永远误报。**必须改安装**（探测面与目标之间不夹介质），调参是白费功夫。
    - **判据**（固化在 `DistanceDiagAnalysis.nearFieldSaturated`）：无人阶段读数上界 ≤ 50cm **且**大半仍判"有人" → `NEAR_FIELD_SATURATION`，**优先于**"误报主导"（两者表现相似但处置相反，所以顺序不能反）。
    - **用户 A/B 实测**：同一模块，感应面隔门板 → 恒报 30cm、不可用；**感应面直接朝外 → 灵敏好用**。此前那块薄门板可用 → 说明穿门可行性取决于门板材质/厚度/有无金属层，**不能一概而论**（对应 Q6）。
    - **教训**：v0.5.4 及之前的指导把"距离一直不变"一律归为"阈值低于底噪"，建议"调高静止阈值"——在近场饱和下这条建议是错的（会连人一起屏蔽）。凡"失效归因"类文案，都要先区分"读数是否被钉在最小值"。
25. **LD2410C 协议里没有板载 LED 控制命令（2026-10-07 核实）**：协议 V1.09 PDF 全表 + 官方 Demo 源码均无灯控命令。官方 Demo `BaseVolume.kt` 里的 `HMD02_CMD_OPEN/CLOSE`（F91B/F91C 开/关灯）属于**另一款产品 HMD02 感应灯模块**（专用 UUID `00010203-...`、独立协议），与 LD2410C 无关。LD2410C 板载指示灯随数据上报闪烁，软件无法关闭，只能物理遮蔽；**外接 LED（OUT 引脚）**可通过光敏辅助控制 0x00AD 间接控制（state=0 关闭联动，设备管理页已加实验区；本机旧固件 1.00.68 是否支持 0x00AE/0x00AD 待实测）。

## 6. 名词速查

- **距离门（Gate）**：雷达把探测距离切成最多 8 段（默认每段 0.75m），每段可独立设灵敏度；
- **工程模式**：上报帧附带每个距离门实时能量的调试模式；
- **无人持续时间**：人离开后保持"有人"输出的延时（默认 5s），影响"离开"事件时机；
- **底噪检测**：无人环境下测量各门背景能量，用于科学设定灵敏度阈值（设备侧 `0x000B`，结束后会**自动写入它自己的建议灵敏度**）；
- **无人基线定参**：无人时测出各门能量的"浮动上界"（口径可选 p95 典型上界 / 绝对最高值），把灵敏度设在「上界 + 边距」。与底噪检测互补但不可同时进行（见 §2.22、Q11）；
- **阶段标记（phase）**：两步引导流程给样本打的标签（1=无人 / 2=有人 / 0=未分段），是算出**误报率/检出率**的前提（见 §2.23）；
- **近场饱和**：紧贴天线的介质（门板/玻璃/金属）反射强于目标回波，导致距离被钉在最小值、无人也报有人。**阈值对它无解，只能改安装**（见 §2.24）；
- **灵敏度**：能量阈值（0~100），能量 > 灵敏度才判定有人；设 100 = 屏蔽该距离门；
- **三档监控模式**：静默记录 / 有人提醒 / 全量调试（通知引擎的总开关）。
